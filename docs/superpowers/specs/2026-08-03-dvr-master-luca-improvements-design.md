# DVR Master — Luca Improvement Round Design

**Date:** 2026-08-03
**Status:** Implemented and locally verified; pending production rollout
**Repository:** `gunnit/n2o-dvr-platform`
**Base revision:** `60267a7047ef7665388770fb6e6c87609db305ea`

## 1. Context

Luca Marchetti sent the email **“N2O VERA - DOCUMENTO RISCHIO MASTER”** with thirteen attachments showing requested corrections to the generated DVR Master. The feedback applies only to `dvr_master`; other document generators must keep their existing cover, branding, ordering, and layout behavior.

The approved direction is an end-to-end data-fidelity fix. A generator-only patch is insufficient because environment photos are uploaded by the API service but the DVR is generated by a Celery worker mounted on a different Render disk. A broader platform redesign using object storage and an equipment many-to-many model is outside this change.

The current focused baseline is clean: 31 DVR, TOC, branding, and revision tests pass before implementation.

## 2. Goals

1. Implement all eleven requested DVR Master corrections.
2. Preserve every saved user value that belongs in the DVR.
3. Make document output deterministic from the operator-controlled order.
4. Fix production photo rendering across separate Render services.
5. Keep failures visible and attributable without making one unavailable photo abort the full document.
6. Add regression coverage at the data, renderer, DOCX XML, migration, and rendered-layout levels.

## 3. Non-goals

- Do not change the visual identity or cover of MMC, VDT, HACCP, POS, DUVRI, PEE, or other generators.
- Do not replace the current Render deployment with object storage in this round.
- Do not remodel equipment as a many-to-many entity.
- Do not alter the N2O risk-index invariant `I = 2*D + P`.
- Do not send workplace photos, identity data, or health data to an AI service.
- Do not modify Luca's source attachments or commit them to the repository.

## 4. Approved Architecture

The work is divided into five bounded units:

1. **DVR input normalization** — establishes saved order and distinguishes employees from external safety consultants.
2. **DVR content fidelity** — groups global equipment, emits every effective risk, restores person-level risk rows, and maps every improvement field.
3. **Photo transport and normalization** — creates a database-backed document image that both Render services can access.
4. **DVR presentation** — supplies the VERA cover, topic separators, alignment, landscape improvement table, and declaration/signature layout.
5. **Verification** — focused unit tests, integration generation, migration tests, and visual PDF inspection.

These units communicate through explicit helpers and model fields. Other generators continue using the shared loader and existing branding behavior unchanged.

## 5. Detailed Design

### 5.1 DVR-only N2O VERA cover

Add a dedicated project asset for the DVR Master cover, derived from Luca's attached N2O VERA image. Use a precise image edit to remove only the small Gemini mark while preserving:

- the N2O flame mark;
- the silver `N2O` wordmark;
- the green and red bars;
- the word `VERA`;
- the exact tagline `Valutazione Evoluta dei Rischi Aziendali`;
- the original proportions, colours, and white background.

The source attachment has SHA-256 `d7dee7636231486729ca46f36795263f934f8d9546c9adcd2fd4a94592ba1656`. Accept the edited asset only after visual inspection confirms the exact text and logo geometry and an image comparison confirms that changes are confined to the watermark region. Reject and retry any edit that changes the wordmark, tagline, colours, or proportions.

The final asset lives under `backend/assets/` with a DVR-specific name. `_add_cover_page()` reads this asset directly instead of resolving organization branding. This prevents an uploaded organization logo from overriding Luca's required DVR cover and prevents the change from leaking into other document types.

The cover retains the legally and operationally useful elements:

- document title and legal subtitle;
- client company name and registered address;
- P.IVA and ATECO when present;
- revision and generation date.

Remove the crossed-out `Documento elaborato da` consultancy letterhead block and its contact/RSPP details from this cover. No other page loses organization data required by the document.

### 5.2 Saved order and employee classification

After `DVRMasterGenerator.load_data()` returns, normalize only the DVR's in-memory lists:

- people: `(ordine, created_at, id)`;
- environments: `(ordine, created_at, id)`.

Null or legacy order values sort after valid values, followed by creation time and UUID for a deterministic tie-break. The normalized lists are passed unchanged through Part I, Part III, risk-specific tables, and Part IV. The shared base loader remains unchanged so other generators do not receive an unrequested ordering change.

The generation data flow is explicit: load shared data, establish DVR order, classify `employee_persons`, then load DVR extras using the employee count. This prevents external consultants from affecting employee-count thresholds calculated inside the extras loader.

Define one DVR helper for an external safety consultant:

```text
is_esterno AND (ruolo_rspp OR ruolo_medico_competente)
```

Create `employee_persons` by excluding only that class. Use `employee_persons` for:

- the occupational/employee roster;
- effective employee counts;
- worker-count thresholds and worker training summaries.

Continue using the complete people list for:

- Datore di Lavoro, RSPP, RLS, and Medico role tables;
- emergency-role tables;
- declaration and signature tables.

An internal employee who also serves as RSPP or Medico remains in the occupational roster.

### 5.3 Global equipment deduplication

Keep one equipment row per environment in the database and in Part III. Only the global Part I table is consolidated.

Group equipment by a normalized description consisting of trimmed text, collapsed internal whitespace, and Unicode-aware case folding. For each group:

- display the first saved description in uppercase;
- collect unique environment names in saved environment order;
- join environment names in one cell with commas;
- display `SI` or `NO` when every record agrees on CE marking;
- display `MISTO` when CE values conflict;
- apply the same unanimous-or-`MISTO` rule to periodic inspections.

Rows stay ordered by the earliest associated environment order, followed by the earliest source-row position. This retains operator intent while eliminating visual duplicates.

### 5.4 Production-safe environment photos

#### Data model

Add two nullable fields to `AmbienteFoto`:

- `document_image_bytes`: normalized binary image used by document workers;
- `document_image_content_type`: the normalized MIME type, normally `image/jpeg`.

The existing original filename, MIME type, size, and disk path remain intact for current upload and preview behavior. The migration is additive and backward compatible.

#### Normalization

Create one reusable image-normalization service. It:

- registers HEIC/HEIF decoding through a pinned `pillow-heif` runtime dependency;
- applies EXIF orientation;
- converts the image to RGB on a white background when alpha is present;
- limits the longest edge to 2000 pixels without enlargement;
- encodes a JPEG at quality 88 with optimization;
- enforces a maximum normalized payload of 3 MB by reducing quality and then dimensions within documented lower bounds;
- rejects undecodable content with a typed, filename-safe error.

This database copy is bounded and suitable for DOCX generation; the original upload limit remains 10 MB.

#### New uploads

The upload endpoint validates the original as it does today, produces the normalized document copy, writes the original to the API disk, and commits both metadata and normalized bytes in one database transaction. If normalization fails, the upload returns the existing Italian unsupported-file error and does not create a photo row.

If the database commit fails after the original file is written, the endpoint removes that new file best-effort so it does not leave an orphan on the API disk.

#### Existing uploads

Before enqueuing a DVR Master generation, the API service backfills any photo row whose normalized bytes are missing:

1. read the legacy path from the API disk;
2. normalize the image;
3. persist normalized bytes and MIME type;
4. commit before dispatching the worker.

Put this logic in one async preflight helper used by every single-document and batch-document dispatch path that can enqueue `dvr_master`. The synchronous Celery dispatch helper remains responsible only for dispatch.

If both the legacy disk file and normalized database copy are missing, generation is still allowed. The worker records an explicit unavailable-photo line for that filename in the relevant environment section.

The authenticated photo-content endpoint falls back to normalized database bytes when the original disk file is unavailable, restoring previews for backfilled records.

#### DVR rendering

The worker loads every photo row for the environment in creation order and attempts all ten permitted photos, not only the first three. It prefers `document_image_bytes`, then falls back to an accessible local path for local development and unmigrated installations. It embeds through `BytesIO`, numbers captions consecutively, and emits one filename-specific placeholder for each unavailable image.

Every failure is logged with the photo UUID and sanitized filename. Exceptions are not silently swallowed, and one failed photo does not abort the DVR.

### 5.5 Effective risk emission

The renderer treats child `PericoloValutazione` rows as the source of truth whenever a parent has children:

- with children: emit every child whose `applicabile` is true, in relationship order;
- with children but none applicable: emit no legacy parent fallback;
- without children: emit the parent only when the parent `applicabile` is true.

A category is marked `SI` and receives a risk table when it has at least one effective row. This guarantees that an applicable evaluated child prints even if its parent flag is stale, while disabled children remain absent. The synthetic VDT rule continues to work independently.

As defense in depth, every child create, update, delete, and replace-all batch write synchronizes the parent `applicabile` flag to whether any persisted child is applicable. Renderer correctness does not depend on that synchronization.

### 5.6 Person-level specific-risk table

Replace the current role-level union table with the template's person-level shape:

```text
Nominativo | Mansione | Rischio specifico
```

For each employee in `employee_persons`, calculate only that person's labels from:

- VDT exposure;
- special-equipment qualifications;
- `rischi_specifici_codes`.

Emit one row per exposed person in saved people order. Join multiple labels in the third cell. Two people with the same role never inherit each other's risks. People with no specific-risk signal are not added to this specific-risk table.

### 5.7 DPI placeholder alignment

Keep normal text alignment unchanged. In each DPI table, when the `Marca / Modello` value is `-` or `—`, set:

- paragraph alignment to horizontal centre;
- cell vertical alignment to centre.

The behavior is local to the DPI `Marca / Modello` placeholder and does not globally centre every dash in the document.

### 5.8 Topic separator pages

Every level-2 DVR topic receives a dedicated separator page. Level-3 subsections stay inline. This includes:

- Part I chapters;
- Part II methodology chapters;
- each Part III environment and its level-2 tail topics such as specific risks, DPI, signage, and training;
- the improvement program, each Part IV procedural chapter, related documents, and the employer declaration.

Use one `_add_topic_separator()` abstraction that creates the actual level-2 heading used by the TOC, styles the page as a divider, and inserts a page break after it. It does not repeat the same heading on the following content page.

At the first topic in each Part, render the Part's level-1 heading on the same separator page as a smaller part label. This preserves one H1 TOC entry per Part without creating two consecutive divider pages. Subsequent topic separators carry the current Part label as non-heading context.

The helper owns page boundaries so callers do not add adjacent duplicate breaks or accidental blank pages.

### 5.9 Complete improvement-program mapping

The improvement program prints all seven user-facing values:

1. Priorità;
2. Rischio (`misura`);
3. Misura di Miglioramento (`misura_miglioramento`);
4. Attività / Procedura (`procedura`);
5. Risorse;
6. Responsabile;
7. Scadenza.

`ordine` continues to control row order and provenance UUIDs remain internal. Risk-priority colour remains an additional visual signal, never the only representation of priority.

Render this table in a landscape section with explicit column widths and repeating headers, then restore portrait orientation before the next topic. This avoids hiding saved fields in an unreadable seven-column portrait table.

### 5.10 Employer declaration and signatures

The declaration is a dedicated level-2 topic, so its separator is followed by a fresh content page. The content page contains:

- the complete employer declaration;
- place and date;
- the existing four-role signature grid.

Give each populated signature cell at least 3 cm of signing height. Set exact-at-least row heights, mark rows `cantSplit`, and apply keep-with-next rules to the declaration's closing paragraphs so the signature table is not orphaned. Preserve the 2×3 role layout and all names.

The content is designed to fit one page at normal A4 margins. If Word reflow caused by unusually long names forces a second page, no signature row may split across pages.

## 6. Error Handling and Observability

- A missing photo produces a visible, filename-specific placeholder and a structured warning log.
- An unsupported new image fails the upload transaction with the existing Italian validation message.
- Legacy photo backfill failures are logged and do not block document dispatch.
- VERA asset loading failure falls back to a visible `[LOGO N2O VERA NON DISPONIBILE]` marker; it must not silently substitute an unrelated organization logo.
- A malformed equipment description falls into a single `—` group without crashing generation.
- Empty improvement fields render `—`; populated fields must never be replaced by another model field.
- Risk tables use the same risk-index calculator as today; no local formula is introduced.

## 7. Test Strategy

### 7.1 Unit and renderer tests

Add focused tests proving:

- people and environments render in saved order rather than alphabetic order;
- only external RSPP/Medico are excluded from employee views and counts;
- external consultants remain in role and signature tables;
- identical global equipment collapses to one row with ordered environment names;
- mixed CE and inspection values render `MISTO`;
- parent-false/applicable-child risks print;
- disabled children do not print and do not resurrect a parent fallback;
- childless applicable legacy parents still print;
- two people sharing a role retain their own names and risk labels;
- only the DPI placeholder cell has both centre alignments;
- all seven improvement fields print in `ordine` order;
- all ten photos can create inline shapes and captions;
- unavailable photos produce explicit placeholders;
- HEIC input normalizes and embeds successfully.

### 7.2 API and migration tests

Verify:

- migration upgrade adds both nullable photo fields;
- migration downgrade removes only those fields;
- new uploads persist normalized image bytes;
- invalid content rolls back without a photo row;
- DVR generation preflight backfills a legacy API-disk photo before dispatch;
- content streaming falls back to database bytes;
- child-risk batch updates synchronize the parent flag.

### 7.3 DOCX structure tests

Inspect DOCX/XML to confirm:

- the exact approved VERA asset is embedded and the old fallback asset is absent from the DVR cover;
- the consultancy letterhead strings are absent from the cover;
- each level-2 topic occurs once in the TOC and once as a separator heading;
- there are no adjacent duplicate page breaks;
- the improvement table section is landscape and the following topic is portrait;
- declaration content starts after its separator;
- signature rows have the required height and `cantSplit`.

### 7.4 End-to-end and visual verification

Generate the full Acme DVR fixture plus a targeted Luca-style fixture containing:

- out-of-alphabetical saved order;
- external RSPP and Medico;
- duplicate equipment across environments;
- ten mixed JPG/PNG/HEIC photos;
- stale parent risk flags with applicable children;
- two same-role workers with divergent risks;
- complete improvement rows.

Run the document auditor, convert the DOCX to PDF, and visually inspect at minimum:

- cover;
- two representative separator pages;
- ordered occupational and environment sections;
- consolidated equipment table;
- environment photos;
- risk table completeness;
- person-level risk table;

Record page count and inspect for blank pages, clipped tables, split signatures, distorted logo text, or altered VERA colours.

## 8. Data and Privacy

Environment photos remain tenant-scoped and protected by existing authenticated endpoints. The new database copy is a resized document derivative, not an AI input. No photo, identity document, codice fiscale, or health information leaves the application for this feature.

The migration does not attempt a database-side filesystem backfill because PostgreSQL cannot read the API service's Render disk. Backfill happens only in the authenticated API generation path that has access to that disk.

## 9. Rollout and Compatibility

The photo migration is nullable and additive, so old API and worker code tolerate it during a rolling deployment. Deploy order is:

1. apply the migration;
2. deploy API and worker code from the same commit;
3. generate a staging DVR containing legacy and new photos;
4. verify document bytes, PDF rendering, and worker logs;
5. regenerate the affected client DVR after production verification.

Existing uploaded photos are backfilled the next time a DVR Master is requested, provided the original remains on the API disk. A row whose original is already missing remains represented by an explicit unavailable-photo line rather than disappearing.
